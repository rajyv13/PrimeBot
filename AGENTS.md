# PrimeBot — Agent Notes

## Dashboard (Vercel) auth — known gotchas

The dashboard is deployed to Vercel as a serverless Express app (`dashboard/server.js` via `vercel.json`). Login uses Discord OAuth2 → `/auth/callback` → redirect to `/`. **The dashboard is now a server-rendered multi-page app (MPA)**, not a SPA: each route is a real HTML page rendered by Express. The old `dashboard/public/index.html` + `dashboard/public/app.js` SPA are gone.

- `/login` renders the server-side login page (`render/pages.js` `loginPage`); `/auth/discord` starts the OAuth2 flow (the login page's button points there). `/login?error=session_failed` surfaces the reason via `LOGIN_ERRORS` in `render/pages.js`.

Key points that have bitten us before:

- **Session store must use SSL.** Production Postgres on Vercel (Neon/Supabase/Vercel Postgres) requires SSL. `buildSessionStore()` reuses the bot's `server/db.js` `pool` (which sets `ssl` from `DATABASE_URL`/`DB_SSL`) rather than a bare `new Pool({ connectionString })`. A non-SSL session pool silently fails every session write → Discord login succeeds but the user is bounced back to the login screen because `/api/me` returns 401.
- **`proxy: true` on express-session** is required so the `x-forwarded-proto: https` header is trusted when deciding whether to set/send the `Secure` session cookie behind Vercel's TLS-terminating proxy.
- The OAuth callback awaits `req.session.save()` and redirects to `/login?error=session_failed` if persistence fails (instead of silently redirecting to a broken dashboard).
- `/login?error=...` renders the server-side login page so the error can be surfaced by `LOGIN_ERRORS` in `dashboard/render/pages.js` (previously the SPA's `renderLogin()`).
- **Don't conflate bot-token 401 with user-token 401.** `requireGuildAdmin` calls `getBotGuild` (uses the BOT token, `Authorization: Bot $DISCORD_TOKEN`). A 401 there means `DISCORD_TOKEN` is missing/invalid on the Vercel deployment — NOT that the user's session expired. It returns 503 (`reason: bot_token_unauthorized`) and leaves the session intact. Only a 401 from `getUserGuilds` (user OAuth access token) destroys the session and redirects to `/login`. The SPA renders a clear "set DISCORD_TOKEN" message on 503.
- Without a valid `DISCORD_TOKEN`, the server list still loads (it uses the user's OAuth token) but every server shows as "bot not added" and opening one fails with the 503 above.
- **Dashboard saves need a cache reload to reach the bot.** The bot and dashboard are separate processes sharing the same Postgres tables, but both `ServerSettingsManager` and `WelcomeSettingsManager` cache all rows in memory at boot and only update the cache on the bot's own writes. A dashboard save writes the DB row directly, so without a reload the bot keeps using stale cached values (looks like "save succeeded but nothing changed"). Both managers now re-read the table on a `setInterval` (`SETTINGS_RELOAD_INTERVAL_MS`, default 30000ms) so dashboard changes take effect within ~30s without a bot restart. `loadSettings()` preserves in-memory-only fields (e.g. `leveling.roleRewards`, which has no DB column) across reloads so they aren't wiped.
- **Same DB requirement:** for dashboard saves to affect the bot, both deployments must point at the same `DATABASE_URL` (and `WELCOME_DATABASE_URL` for welcome settings). If they use different databases, dashboard writes never reach the bot regardless of caching.

## Dashboard page routes (top nav)

The top nav (`render/layout.js` `navHTML`) renders: **Servers** (`/`), **Overview** (`/dashboard`), **Stats** (`/stats`), **Live Polls** (`/live/polls`), **Live Giveaways** (`/live/giveaways`), **Docs** (`/docs`). The old combined `/live` page was split into `/live/polls` + `/live/giveaways`; `/live` 302-redirects to `/live/polls` for back-compat. `public/js/live.js` serves both live pages and reads `window.liveKind` (`'poll'`/`'giveaway'`, injected by an inline `<script>` on each page) to pick `/api/live/polls` vs `/api/live/giveaways`.

- **Stats page** (`render/pages.js` `statsPage` → `/stats`): shows bot stats (server count via Discord REST `getBotGuildCount`, bot identity, version, feature-adoption donuts) and shardnode node health. The dashboard process can't read the bot's in-memory runtime (ping/uptime/guilds.cache) because it runs separately from the bot; it reads the `bot_node_status` + `bot_failover_lock` tables the bot's `utils/nodeFailover.js` writes every ~15s. Endpoints: `/api/stats/bot` (`db.getPlatformStats`) and `/api/stats/nodes` (`db.getNodeStats`). Node roles are `sn1`/`sn2`/`sn3` (priority sn1>sn2>sn3); a node is offline once heartbeat age > 45s (`FAILOVER_THRESHOLD_MS`).

## Auto-reactions save — verified working

The `/guild/:id/reactions` page's "Save auto-reactions" path was exhaustively verified (mock-DB boot + real browser) to work in ALL scenarios: add-rule+save, remove-row+save-empty, toggle, and reload-read-back. The server handler (`upsertServerSettings` writing `server.autoReactions`), the DB round-trip, and `settings-basic.js` `saveAutoReactions` all behave correctly. **If a user reports "auto-reactions not saving", the cause is operational, not code:** see the **Same DB requirement** above — if the bot and dashboard point at different `DATABASE_URL`s, the dashboard's write lands in a different database than the bot reads, so it looks unsaved. Also confirm the bot's `ServerSettingsManager` settings-reload interval has run (≤30s) before concluding a save "didn't take effect".

## Server logging feature

Per-guild logging posts rich embeds of server events (member join/leave, bans/unbans, member role/nickname updates, message edits/deletes, slash-command use) to a log channel and/or a Discord webhook. Configured entirely from the dashboard's **📜 Logging** tab.

- **Shared event catalog:** `utils/logEvents.js` is the single source of truth for loggable event types (key, label, icon, default color, category). The bot, the dashboard (`dashboard/constants.js` → `LOG_EVENTS`), the SPA (`dashboard/public/app.js` `LOG_EVENTS`), and tests all import/mirror it. To add a new event type, add one entry to `LOG_EVENTS` and an event hook that calls `logEvent(client, guildId, { type, ... })`.
- **Delivery:** `utils/serverLogger.js` `logEvent()` checks `isEventEnabled()` (master switch + the event's toggle + `includeBots`), builds an `EmbedBuilder`, and delivers it to (1) `settings.channelId` via `client.channels.fetch().send()` (bot needs View Channel + Send Messages) and (2) `settings.webhookUrl` via a raw HTTPS POST. If both are set, both are used; if neither is set, nothing is sent. Every path is fire-and-forget — a logging failure never throws back into the event handler.
- **Webhook option:** lets logs reach a channel the bot can't see, or be forwarded to an external service that accepts a Discord webhook payload. The dashboard validates that the URL looks like a Discord webhook (`discord.com/api/webhooks/...`) before saving.
- **Settings storage & caching:** `logging_settings` table (migration `migrations/0008_add_logging_settings.sql`, also in `shared/schema.js` as `loggingSettings`) lives in the main `DATABASE_URL` pool (NOT a separate welcome DB). The bot's `LoggingSettingsManager` (`utils/loggingSettingsManager.js`) follows the same pattern as `WelcomeSettingsManager`: in-memory cache, write-through to DB, and a `setInterval` re-read every 5s + ~30s so dashboard saves take effect without a bot restart. Verified end-to-end: a dashboard color/events change appears in the bot's cache within the 5s refresh window.
- **Dashboard API:** `PATCH /api/guilds/:guildId/logging` (guarded by `requireAuth` + `requireGuildAdmin`) accepts a patch of `enabled, channelId, webhookUrl, webhookName, events, includeBots, color`. Settings are included in `getGuildConfig` so the settings page loads them in one fetch.
- **No env vars required:** unlike failover (`FAILOVER_WEBHOOK_URL`) or welcome (`WELCOME_DATABASE_URL`), logging needs no extra env var — it uses the existing `DATABASE_URL` and is configured per-guild from the dashboard.

## Env vars (Vercel)

On Vercel, set in Settings → Environment Variables: `DISCORD_TOKEN`, `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `DATABASE_URL` (with `?sslmode=require` if the host needs SSL), `SESSION_SECRET`, `DASHBOARD_BASE_URL` (= `https://<prod>.vercel.app`), `DISCORD_REDIRECT_URI` (= `<DASHBOARD_BASE_URL>/auth/callback`, registered in the Discord Developer Portal), `WELCOME_DATABASE_URL` (separate pool for welcome settings), `REACTION_DATABASE_URL` (separate pool for reaction-role menus; falls back to `DATABASE_URL` if unset), `AUTOMOD_DATABASE_URL` (separate pool for automod settings/warnings; falls back to `DATABASE_URL` if unset), `TICKET_DATABASE_URL` (separate pool for ticket panels/instances; falls back to `DATABASE_URL` if unset), `LIVE_DATABASE_URL` (separate pool for live giveaways; falls back to `DATABASE_URL` if unset), and `EVENT_DATABASE_URL` (separate pool for event schedules/tasks; falls back to `DATABASE_URL` if unset). `EVENT_EXEC_INTERVAL_MS` (optional, default 5000) controls how often the bot's event scheduler wakes to fire due tasks.

## Reaction roles feature

Self-assignable roles via message reactions. Premium-style modes shipped for free: **normal** (toggle on/off), **sticky** (one-click assign, no toggle-off), **verify** (grant once, e.g. a rules-gate role), and **unique** (only one role from the menu at a time). Roles persist across bot restarts (`persistent`, default on) by re-reading the message's reactions on startup. Configured from the dashboard's **🎭 Reaction Roles** tab or the `/reactionrole` slash command.

- **Two creation flows:**
  - *Bot-created menu:* the bot posts a role embed to a channel, adds the configured reactions, and stores `message_id`/`channel_id`. The dashboard does the same via REST (`sendChannelMessage` + `addMessageReaction`) and captures the resulting message id — the bot starts watching on its next cache reload.
  - *Attach to existing message:* provide a `messageId` + `channelId` for ANY message; the bot adds reactions to it and watches it. Works on a message the bot didn't send (it only needs Add Reactions + Read History in that channel).
- **Storage:** `reaction_roles` + `reaction_role_mappings` tables in the `REACTION_DATABASE_URL` pool (`server/reactionDb.js` → `reactionPool`; falls back to `DATABASE_URL`). Migration `migrations/0009_add_reaction_roles.sql`, also in `shared/schema.js` as `reactionRoles`/`reactionRoleMappings` with relations. Three-pool pattern alongside main `pool` and `welcomePool`.
- **Manager:** `utils/reactionRoleManager.js` (`ReactionRoleManager`) follows the existing settings-manager pattern — in-memory cache keyed by `guildId|channelId|messageId`, write-through to DB, and a `setInterval` re-read every 5s + ~30s so dashboard edits take effect without a bot restart. Constructed in `index.js` (wrapped in try/catch with a no-op stub if the DB is unavailable). Restored on startup in `events/ready.js`.
- **Event handling:** `events/messageReactionAdd.js` / `messageReactionRemove.js` check `client.reactionRoleManager` before the giveaway check. `handleReactionAdd`/`handleReactionRemove` look up the menu, normalize the emoji (`ReactionRoleManager.parseEmojiString` → `name:id` for custom, raw unicode otherwise), enforce `includeBots`, `requiredRoleId`, `exclusiveRoleId`, and the mode semantics, then `member.roles.add`/`remove`. For non-normal modes on reaction-remove, the role is NOT removed (sticky/verify) but `true` is still returned so other handlers skip it. Failures are fire-and-forget (never throw back into the event handler) and the offending reaction is removed when a user reacts with an unmapped emoji.
- **Slash command:** `/reactionrole` (commands/reactionrole.js) with subcommands `create`, `add`, `remove`, `list`, `delete`. Mirrors the dashboard flows; requires Manage Roles + Manage Messages.
- **Dashboard API:** `GET /api/guilds/:guildId/roles` (role list for selectors), `GET/POST /api/guilds/:guildId/reactionroles`, `PATCH/DELETE /api/guilds/:guildId/reactionroles/:id`. All guarded by `requireAuth` + `requireGuildAdmin`. The SPA panel lives in `dashboard/public/app.js` (`reactionRolesPanelHTML` + `bindReactionRolesEvents`). `getGuildConfig` now returns `reactionRoles` alongside `server`/`welcome`/`logging`. Roles persist with DB-only writes; the bot picks them up via its cache reload (no direct bot↔dashboard IPC).
- **Same-DB requirement (as with welcome/logging):** for dashboard-created menus to reach the bot, both deployments must point at the same `REACTION_DATABASE_URL` (or the same `DATABASE_URL` fallback). Different DBs → dashboard writes never reach the bot.

## Premium Automod feature

Premium-style automod shipped for free (PrimeBot's motto — **not** gated behind premium). Scans every message against per-guild rules and runs an action; a warnings ledger with escalation ties manual and automatic moderation together. Configured from the dashboard's **🛡️ Automod** tab, the `/automod` slash command, or the prefix commands `warn`/`unwarn`/`warnings`/`mute`/`unmute` (existing `kick`/`ban` still work too).

- **Shared rule catalog:** `utils/automodRules.js` is the single source of truth for rule types (`RULES`), actions (`ACTIONS`), `normalizeRules()`, `normalizeActions()`, `normalizeWarnActions()`, `normalizeDmMessages()`, `metaFor()`, `renderDmMessage()`, `DEFAULT_DM_MESSAGES`, and the pure `matchRule(rule, ctx, spamState)` matcher. The bot, the dashboard (`dashboard/constants.js` → `AUTOMOD_RULES`/`AUTOMOD_ACTIONS`), the SPA (`dashboard/public/app.js` `AUTOMOD_RULES`/`AUTOMOD_ACTIONS`), and tests all import/mirror it. To add a new rule type, add one entry to `RULES` and a `case` in `matchRule()`.
- **Rule types:** `blockedWords` (word list), `invites` (discord.gg/invite links), `links` (any URL), `badLinks` (phishing/impersonation domains + scam lures, extensible via `words`; real hosts whitelisted), `nsfw` (built-in NSFW term list + custom `words`), `repeatedChars` (run of the same char), `newAccount` (author account age < threshold days — reads `ctx.authorCreatedAt`), `mentions` (mass @ count), `spam` (rapid/duplicate messages within a window — stateful via a `spamWindow` Map keyed by `guildId|userId`), `caps` (% uppercase), `emojiSpam`, `newlines` (wall of text), `zalgo` (combining marks).
- **Multi-action punishment:** each rule carries an `actions` array (legacy single `action` string still accepted and mirrored as `actions[0]`). A user can select multiple punishments per rule — e.g. `delete + warn + ban`. `delete` is always applied first; the rest run in order. `normalizeActions()` dedupes and validates. `scanMessage` returns `{ rule, actions, reason }`.
- **DM notifications:** when `dmEnabled` is on (default), the bot DMs the punished member for each action using `renderDmMessage()` with templates from `DEFAULT_DM_MESSAGES` (overridable per-guild via `dmMessages`). Placeholders: `{server}`, `{reason}`, `{action}`, `{threshold}`. Covers `delete`/`warn`/`timeout`/`kick`/`ban`/`escalation`.
- **Warn escalation (multi-action):** `warnActions` array (top-level setting) lets a guild escalate through several punishments at once when `warnThreshold` is reached (e.g. `timeout,ban`). Legacy `warnAction` is kept in sync as `warnActions[0]`. Escalation skips `delete`/`warn` (pointless) and clears the member's warnings afterward.
- **Appeals service:** `automod_appeals` table (migration `0011`, also `shared/schema.js` `automodAppeals`) stores member-filed appeals (`pending`/`approved`/`denied`, plus a `reversed` flag). Members file via `/appeal file` (or dashboard); moderators review via `/appeal list|approve|deny` or the dashboard Appeals panel. Approving an appeal reverses the action — `_reverseAction()` unbans / removes timeout / removes the mute role. Since bot and dashboard share only the DB, the bot runs a `_startAppealReversalPoller()` (`APPEAL_POLL_INTERVAL_MS`, default 15s) that picks up dashboard-approved (`status='approved' AND reversed=false`) appeals and reverses them, then marks `reversed=true`. The `/appeal approve` slash path reverses immediately and sets `reversed` so the poller won't double-process. New appeals are posted to the configured `appealChannelId` for moderators.
- **Manager:** `utils/automodManager.js` (`AutomodManager`) follows the existing settings-manager pattern — in-memory cache keyed by `guildId`, write-through to DB, and a `setInterval` re-read every ~30s (`SETTINGS_RELOAD_INTERVAL_MS`) + 5s refresh so dashboard edits take effect without a bot restart. Constructed in `index.js` (wrapped in try/catch with a no-op stub if the DB is unavailable). Restored on startup in `events/ready.js`.
- **Scanning:** `events/messageCreate.js` calls `client.automodManager.scanMessage(message)` after prefix resolution (only when `isEnabled(guildId)`); if it returns truthy (message actioned/deleted) the handler returns and stops processing. Exempt roles/channels + admins are skipped. Enforcement (`scanMessage` → `_enforce` → `_executeAction`) deletes the message, applies each action, posts an embed to the configured log channel, and calls `logEvent()` (server logging) with type `memberUpdate`/title `Automod action`. Failures are fire-and-forget (never throw back into the event handler).
- **Warnings + escalation:** `automod_warnings` table groups all warnings (manual `/warn` and automod `warn` actions) by `(guild_id, user_id)`. When a member's total reaches `warnThreshold`, `_applyEscalation()` runs each `warnActions` action and clears their warnings. `warnMember`/`muteMember`/`unmuteMember` accept either a prefix `Message` or a slash `CommandInteraction` (use `_moderatorId()` to read `.author?.id || .user?.id`).
- **Storage & caching:** `automod_settings` + `automod_warnings` + `automod_appeals` tables (migrations `migrations/0010_add_automod.sql` + `migrations/0011_automod_enhancements.sql`, also in `shared/schema.js` as `automodSettings`/`automodWarnings`/`automodAppeals`) live in the dedicated `AUTOMOD_DATABASE_URL` pool (`server/automodDb.js` → `automodPool`; falls back to `DATABASE_URL` if unset) — the same three-pool pattern as `welcomePool`/`reactionPool`. The bot's manager re-reads every ~30s. **Same-DB requirement:** for dashboard saves to reach the bot, both deployments must point at the same `AUTOMOD_DATABASE_URL` (or the same `DATABASE_URL` fallback). Different DBs → dashboard writes never reach the bot regardless of caching. New `automod_settings` columns: `warn_actions`, `dm_enabled`, `dm_messages`, `appeal_channel_id`.
- **Commands:** Slash — `/automod` (subcommands `enable`/`disable`/`status`/`list`/`addrule`/`removerule`/`set`; `addrule` takes `actions` as a comma-separated list and `set` takes `warn_actions`/`dm_enabled`/`appeal_channel`), `/appeal` (subcommands `file`/`list`/`approve`/`deny`), `/warn`, `/unwarn`, `/warnings`, `/mute`, `/unmute`. All auto-registered via `deploy-commands.js` (reads every `.js` in `commands/`). Prefix equivalents live in `events/messageCreate.js`'s `switch(commandName)` near `kick`/`ban`. All require `ModerateMembers` (mod actions) or `ManageGuild` (`/automod` config, `/appeal list|approve|deny`); `/appeal file` is open to all members.
- **Dashboard API:** `PATCH /api/guilds/:guildId/automod` (guarded by `requireAuth` + `requireGuildAdmin`) accepts `enabled, logChannelId, muteRoleId, exemptRoleIds, exemptChannelIds, rules, warnThreshold, warnAction, warnActions, dmEnabled, dmMessages, appealChannelId`. Warnings: `GET /api/guilds/:guildId/automod/warnings` + `DELETE .../automod/warnings?userId=`. Appeals: `GET/POST /api/guilds/:guildId/automod/appeals` + `PATCH .../automod/appeals/:id` (`{approved, note}` — approval triggers the bot's reversal poller). Settings included in `getGuildConfig` (`automod`) so the settings page loads in one fetch. `getPlatformStats` adds an `automod` donut on the login screen.
- **Env var:** `AUTOMOD_DATABASE_URL` (optional, separate pool for automod tables; falls back to `DATABASE_URL` if unset — so it works in single-DB setups with zero extra config). `APPEAL_POLL_INTERVAL_MS` (optional, default 15000) controls how often the bot reverses dashboard-approved appeals. Set in Vercel → Environment Variables alongside the others. Configured per-guild from the dashboard or `/automod`.

## Premium Ticket panel feature

Premium-style ticket panels shipped for free (PrimeBot's motto — **not** gated behind premium). Members click an open button on a panel message to create a private ticket channel; support roles are granted access, ping roles are mentioned, and a close/reopen (and optional claim) control row is posted inside the ticket. **Ticket panels are configurable ONLY from the dashboard** — slash (`/ticket`, `/createticket`, `/tickethistory`) and prefix (`ticket`, `createticket`, `thelp`, `tcreate`, `createt`, `thistory`) commands all reply with `🎫 Ticket feature can only be used by dashboard.` Legacy `create-ticket`/`close-ticket`/`ticket_toggle` buttons likewise reply with that notice. Only the panel open/close/reopen/claim buttons (customId `ticketpanel:open:<id>` / `ticketpanel:close` / `ticketpanel:reopen` / `ticketpanel:claim`) are active.

- **Dashboard-only configuration:** `utils/ticketManager.js` (`TicketPanelManager`) is the single source of truth. The dashboard SPA's **🎫 Tickets** tab (`ticketsPanelHTML` + `bindTicketEvents` in `dashboard/public/app.js`) builds panels with a full editor: message type (embed or plain text), embed title/description/content/footer/thumbnail/image/color, open button label/emoji/style, close button label/emoji, optional claim button label/emoji, ticket channel name + Discord category id, support roles (can see tickets), ping roles (mentioned on open), per-user open limit, ask-for-reason toggle, in-ticket welcome message, and an enabled switch. Each panel card has Send/Resend, Update message, Rename, Clone, Edit, Delete actions.
- **Premium features:** embed editor with all field types (title, description, footer, thumbnail, image, color, timestamp, content above embed), plain-text message type alternative, customizable open/close/claim buttons with all Discord button styles (Primary/Secondary/Success/Danger), per-user open-ticket limits with cooldowns, and **status-based channel name templates** (open/claimed/closed). `buildPanelMessage()` produces an embed or plain message with the open button; `buildControlMessage()` produces the in-ticket control row (close + optional claim + rename).
- **Status-based channel renaming:** each panel carries `openNameTemplate` / `claimedNameTemplate` / `closedNameTemplate` (defaults `(open) {name}` / `(solved) {name}` / `(closed) {name}`). Placeholders: `{name}` (panel.ticketName or opener username), `{username}`, `{id}`, `{panel}`. The bot renames the ticket channel on open, claim, close, and reopen via `_setTicketName()` (fire-and-forget; an empty template = no rename for that state). Templates are sanitized to Discord channel naming rules (lowercase, no spaces, ≤100 chars).
- **Manual rename:** the in-ticket control row also has a **✏️ Rename** button (`ticketpanel:rename`) that opens a modal where the owner, support staff, or an admin can type a new channel name; `handleRename()` shows the modal and `handleRenameSubmit()` applies it (routed via `interactionCreate.js`'s modal-submit branch).
- **Panel clone/rename:** `cloneTicketPanel()` / `renameTicketPanel()` in `dashboard/db.js` + `clonePanel()` / `renamePanel()` on the manager. Clone duplicates all fields with a new name (defaults to `<name> (copy)`); rename changes only the name. Both surface in the dashboard via per-card Clone/Rename buttons.
- **Send + update by message id:** `sendPanelToChannel()` posts a panel to a channel and stores `channelId`/`messageId`. `updatePanelMessage()` re-renders an existing message (by provided message id or the panel's last sent message) — used by the dashboard's "Update message" button. Both use the bot's REST client when invoked server-side.
- **Button routing:** `events/interactionCreate.js` routes `ticketpanel:*` customIds to `handleOpen`/`handleClose`/`handleReopen`/`handleClaim`/`handleRename` (and the `ticketpanel:rename` modal submit → `handleRenameSubmit`). `handleOpen` checks the per-user open limit + cooldown, creates a private channel (named via the open template, or `ticket-<username>`/the configured `ticketName` when no template is set) under the optional category, grants support roles View Channel, pings ping roles, posts the welcome message + control row, and persists a `ticket_instances` row. Close archives/deletes the channel, applies the closed name template, and marks the instance `closed`; reopen re-opens it and re-applies the open template; claim applies the claimed template.
- **Storage & caching:** `ticket_panels` + `ticket_instances` tables (migration `migrations/0012_add_tickets.sql`, also in `shared/schema.js` as `ticketPanels`/`ticketInstances` with relations) live in the dedicated `TICKET_DATABASE_URL` pool (`server/ticketDb.js` → `ticketPool`; falls back to `DATABASE_URL` if unset) — the same multi-pool pattern as `welcomePool`/`reactionPool`/`automodPool`. The manager keeps in-memory maps (`_panels`, `_byMessage`, `_byChannel`) and re-reads every ~30s (`SETTINGS_RELOAD_INTERVAL_MS`) + 5s refresh so dashboard edits take effect without a bot restart. `restorePanels()` (called from `events/ready.js`) re-binds live panel messages and open tickets on startup.
- **Manager init:** constructed in `index.js` (wrapped in try/catch with a no-op stub if the DB is unavailable) as `client.ticketPanelManager`, with `client.ticketManager` kept as a legacy alias. Restored on startup in `events/ready.js`.
- **Dashboard API:** `GET/POST /api/guilds/:guildId/tickets`, `PATCH/DELETE /api/guilds/:guildId/tickets/:id`, `POST .../tickets/:id/clone`, `POST .../tickets/:id/rename`, `POST .../tickets/:id/send`, `POST .../tickets/:id/update`. All guarded by `requireAuth` + `requireGuildAdmin`. Settings included in `getGuildConfig` (`ticketPanels`) so the settings page loads them in one fetch. `getPlatformStats` adds a `tickets` donut on the login screen.
- **Same-DB requirement (as with welcome/reaction/automod):** for dashboard-created panels to reach the bot, both deployments must point at the same `TICKET_DATABASE_URL` (or the same `DATABASE_URL` fallback). Different DBs → dashboard writes never reach the bot regardless of caching.
- **Env var:** `TICKET_DATABASE_URL` (optional, separate pool for ticket tables; falls back to `DATABASE_URL` if unset — works in single-DB setups with zero extra config). Set in Vercel → Environment Variables alongside the others. Configured per-guild only from the dashboard.

## Live giveaway feature

Cross-server giveaways — the giveaway counterpart to live polls (the existing `$lpoll`/`/lpoll` system). Created with `$lgiveway` (prefix) or `/lgiveway` (slash), shared via a **giveaway ID** + **pass code**, joinable from ANY server via `$lgiveway join <key>` or the 🎉 **Join Giveaway** button. Subcommands in both prefix and slash: `create`, `join`, `results`, `end` (creator only), `list`.

- **Manager:** `utils/liveGiveawayManager.js` (`LiveGiveawayManager`) mirrors `LivePollManager` — in-memory cache keyed by `giveawayId`, write-through to DB, `checkExpiredGiveaways()` sweep (called from `events/ready.js` every 60s) that ends giveaways whose `ends_at` has passed and edits the original message + announces winners. Constructed in `index.js` as `client.liveGiveawayManager` (with a memory-only stub during the early boot fallback). Uses raw SQL against the dedicated `livePool` (no drizzle) so it works in a database separate from the bot's main schema.
- **Storage:** `live_giveaways` + `live_giveaway_participants` + `live_giveaway_winners` tables (migration `migrations/0013_add_live_giveaways.sql`, also in `shared/schema.js` as `liveGiveaways`/`liveGiveawayParticipants`/`liveGiveawayWinners` with relations) in the dedicated `LIVE_DATABASE_URL` pool (`server/liveDb.js` → `livePool`; falls back to `DATABASE_URL` if unset) — the same multi-pool pattern as the other features.
- **Slash command:** `/lgiveway` (`commands/lgiveaway.js`) with subcommands `create`/`join`/`results`/`end`/`list`. Auto-registered via `deploy-commands.js`. Prefix equivalents live in `events/messageCreate.js` (`case "lgiveway"` + `handleLiveGiveaway*` helpers).
- **Button routing:** `events/interactionCreate.js` routes `lgive_<giveawayId>` customIds to `joinGiveaway()` (defers, joins, refreshes the embed + button). Mirrors the `vote_<pollId>_<i>` handling for live polls.
- **Same-DB requirement (as with the other features):** for dashboard views to reflect the bot's state and any dashboard-driven changes to reach the bot, both deployments must point at the same `LIVE_DATABASE_URL` (or the same `DATABASE_URL` fallback).
- **Env var:** `LIVE_DATABASE_URL` (optional, separate pool for live giveaway tables; falls back to `DATABASE_URL` if unset — works in single-DB setups with zero extra config). Configured from the bot commands (no dashboard creation).

## Live dashboard page

The dashboard has a dedicated **Live** page (top-nav link `/live`, route `renderLive` in `dashboard/public/app.js`) that shows two panels: **📊 Live Polls** and **🎉 Live Giveaways**. Each panel has a separate **🟢 Running** list and **🔴 Ended** list (ended only shows winners — for polls the winning option text(s); for giveaways the winner user ids). Each running card has a **Join** button that opens a floating window (modal) showing the exact command to run (`$lpoll join <key>` / `$lgiveway join <key>`) with a copy button. The dashboard cannot join on behalf of a Discord user (it needs a guild context + member), so it surfaces the command instead.

- **API:** `GET /api/live` (guarded by `requireAuth`) returns `{ runningPolls, endedPolls, runningGiveaways, endedGiveaways }`. Live polls are read from the main `pool` (`live_polls` etc.); live giveaways are read from the `livePool`. All reads degrade to `[]` on a missing/unreachable DB.
- **DB functions:** `getLivePolls` / `getEndedLivePolls` (main pool) and `getLiveGiveaways` / `getEndedLiveGiveaways` (live pool) in `dashboard/db.js`. All four now also select `channel_id` (mapped to `channelId`) so the per-server views below can filter by guild.

### Per-server Live tabs (server-features sidebar)

Live polls/giveaways are cross-server (joined via pass code from any server), so the global `/live/polls` + `/live/giveaways` pages show everything across PrimeBot. The per-server **Server features** sidebar (`render/guild.js` `TABS`) now also has **📊 Live Polls** (`/guild/:guildId/live/polls`) and **🎉 Live Giveaways** (`/guild/:guildId/live/giveaways`) entries that show only the items **created in this server** — filtered by matching the row's `channel_id` against the guild's channel set (`discord.getGuildChannels`). Each per-server page links out to the global cross-server Live page.

- **API:** `GET /api/guilds/:guildId/live/polls` and `GET /api/guilds/:guildId/live/giveaways` (guarded by `requireAuth` + `requireGuildAdmin`) return `{ running, ended }` filtered to this guild's channels.
- **Client:** `dashboard/public/js/guild-live.js` serves both tabs (kind derived from the page URL) and reuses the live-card + join-modal markup from the global `live.js`.

## Leveling role rewards (DB-backed)

Per-guild role rewards (a role granted at a given level) were previously held only in the bot's in-memory `ServerSettingsManager` cache and were lost on restart / never synced to the dashboard. They now persist to the `leveling_role_rewards` table in the dedicated `LEVELING_DATABASE_URL` pool (`server/levelingDb.js` -> `levelingPool`; falls back to `DATABASE_URL`), mirroring the welcome/reaction/automod/event caching pattern.

- **Bot (`utils/levelingManager.js`):** `addRoleReward`/`removeRoleReward` are now `async` and write-through to the DB (`upsertLevelingRoleReward`/`deleteLevelingRoleReward`); `getRoleRewards` reads from the in-memory `_roleRewards` cache (falling back to `ServerSettingsManager`). On `initializeDatabase()` the manager loads all rewards via `getAllLevelingRoleRewards()` and starts a 5s refresh + ~30s full re-read (`SETTINGS_RELOAD_INTERVAL_MS`) so a dashboard save or bot restart is reflected without a restart. The old buggy `serverSettingsManager.saveSettings()` call (which never existed) is gone. Callers in `commands/leveling.js` now `await` the add/remove.
- **Dashboard:** `dashboard/db.js` adds `getLevelingRoleRewards`/`setLevelingRoleRewards` (against `levelingPool`); `getGuildConfig` attaches `server.leveling.roleRewards`. The Leveling page renders a Role rewards editor (`dashboard/render/guild-pages.js` `levelingPage` + `dashboard/public/js/leveling.js`) with add/remove/save, and `PUT /api/guilds/:guildId/leveling/rolerewards` (guarded by `requireAuth` + `requireGuildAdmin`) persists them.
- **Same-DB requirement:** for dashboard edits to reach the bot, both deployments must point at the same `LEVELING_DATABASE_URL` (or the same `DATABASE_URL` fallback). The bot picks up dashboard writes via its cache reload (~5s).
- **Higher-role safety:** the dashboard's roles endpoint and page pre-population now exclude roles at/above the bot's highest role (and integration-managed roles) via `getGuildRoles(guildId, { excludeUnassignable: true })` + `getBotHighestRolePosition()`, so neither reaction-role nor leveling reward selectors ever offer a role the bot can't assign (prevents 50007 "Missing Access"). The reaction-role manager (`utils/reactionRoleManager.js`) also DMs a warning embed and removes the reaction if it ever hits an unassignable role. `$role add` / `/role add` with a higher-position role now reply with a detailed warning embed instead of a plain string.

## Event management feature

Premium-style event scheduling. A per-guild "event schedule" has a **countdown** (seconds to start) and a list of **tasks**, each running at a relative offset (seconds from the event start) and performing one action: **lock/unlock/hide/unhide channels**, **add/remove roles**, or **send a text/embed message**. Configured ONLY from the dashboard's **📅 Events** tab.

- **Manager:** `utils/eventManager.js` (`EventManager`) follows the existing settings-manager pattern — in-memory cache (`_byId`/`_byGuild`), write-through to DB, a `setInterval` re-read (~30s `SETTINGS_RELOAD_INTERVAL_MS`) so dashboard edits take effect without a bot restart, plus a self-driving exec loop (`EVENT_EXEC_INTERVAL_MS`, default 5s) that starts events when `start_at` arrives and fires each task when its offset elapses, marking tasks `executed_at` so a bot restart resumes the schedule without double-firing. Constructed in `index.js` as `client.eventManager` (wrapped in try/catch with a no-op stub if the DB is unavailable). Restored on startup in `events/ready.js`.
- **Task actions:** `lock`/`unlock`/`hide`/`unhide` edit `@everyone`'s `SendMessages`/`ViewChannel` permission overwrites on the **selected channel(s)** — the dashboard lets you pick one channel or hold Ctrl/Cmd to select several (never all channels); `addrole`/`removerole` grant/remove target role(s) (`targetType` `role` → to all members; `user` → to the listed user ids); `sendtext` posts a plain-text message to the target channel(s); `sendembed` posts an embed (title/description/color/image) to the target channel(s). `_applyChannelPerm` falls back to the legacy single `channelId` field when `targetIds` is empty. All execution is fire-and-forget per task.
- **Storage:** `event_schedules` + `event_tasks` tables (migration `migrations/0014_add_events.sql`, also in `shared/schema.js` as `eventSchedules`/`eventTasks` with relations) in the dedicated `EVENT_DATABASE_URL` pool (`server/eventDb.js` → `eventPool`; falls back to `DATABASE_URL` if unset) — the same multi-pool pattern. A schedule's `status` is one of `scheduled | running | completed | cancelled`; `triggered` flips true once the event has fired its start so restarts don't re-run offset-0 tasks.
- **Dashboard API:** `GET/POST /api/guilds/:guildId/events`, `PATCH/DELETE /api/guilds/:guildId/events/:id`, `POST .../events/:id/start`, `POST .../events/:id/cancel`. All guarded by `requireAuth` + `requireGuildAdmin`. The SPA editor (`eventsPanelHTML` + `bindEventsTab` in `dashboard/public/app.js`) builds schedules with a countdown + a dynamic task list (offset/action/target/message-or-embed) and per-card Start/Cancel/Delete actions.
- **Same-DB requirement (as with the other features):** for dashboard-created events to reach the bot, both deployments must point at the same `EVENT_DATABASE_URL` (or the same `DATABASE_URL` fallback). Different DBs → dashboard writes never reach the bot regardless of caching.
- **Env var:** `EVENT_DATABASE_URL` (optional, separate pool for event tables; falls back to `DATABASE_URL` if unset — works in single-DB setups with zero extra config). `EVENT_EXEC_INTERVAL_MS` (optional, default 5000) controls the exec loop cadence. Set in Vercel → Environment Variables alongside the others. Configured per-guild only from the dashboard.
